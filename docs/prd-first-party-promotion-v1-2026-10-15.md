## PRD v1.0 完整实施版与 Codex 执行说明

**文档状态：待仓库审计、RFC 评审与业务负责人确认**  
**项目：GeoSub.org**  
**适用执行方：Codex、项目维护者、推广运营负责人**  
**首期实验：14 天**  
**生产权限：本文件不构成生产部署、数据库迁移或真实广告启用授权**

## 1. 项目背景与目标

GeoSub 的核心定位是数字服务价格比较平台。本项目为中文站增加轻量、可配置、可观测、可关闭的自营推广能力，将部分用户引导至轨道商店。

推广必须是独立、明确标识的补充信息，不得改变价格数据库的独立性，不得影响用户查询和比较价格。

首期验证：

1. 中文页面用户是否愿意了解相关商店服务。
2. 首页品牌入口与相关产品详情页分别产生多少有效访问及可核验成交。
3. 推广是否影响核心功能、页面性能、用户体验和搜索表现。

首期不设收入承诺，不以点击量作为唯一成功指标，不承诺推广不会影响 SEO。

### 1.1 已确定的范围

| 页面 | 投放形式 | 单页上限 | 位置 |
|---|---|---:|---|
| 中文首页 | 轨道商店品牌入口 | 1 个 | 核心搜索及主要分类入口之后 |
| 中文 Google One 产品详情页 | 经审核的相关商品或服务推广 | 1 个 | 核心价格比较内容之后、FAQ 之前 |
| 中文 Telegram Premium 产品详情页 | 经审核的相关商品或服务推广 | 1 个 | 核心价格比较内容之后、FAQ 之前 |
| 其他全部页面 | 不展示 | 0 个 | 无 |

“其他全部页面”包括：

- 英文及其他语言版本；
- ChatGPT 及其他产品详情页；
- 地区页、国家价格页、排行榜；
- 文章、搜索结果页及其他工具页。

**允许的是三个具体页面位置，不是整个中文路由下的通用广告位。**

实际语言代码、路由和产品标识必须通过审计确定。不得假设一定存在 `/zh/`、`google-one` 或 `telegram-premium` 等路径。

如果存在简体、繁体等多个中文版本，必须在 RFC 中明确本期允许的具体版本；不得自动将全部中文变体加入范围。

### 1.2 不做的功能

首期不建设：

- AdSense 或其他第三方广告网络；
- 竞价、商家入驻、自助投放、广告结算；
- 多广告轮播和复杂优先级；
- 弹窗、浮层、插屏、自动跳转；
- 在价格表内部插入推广商品；
- 用户画像、个性化推荐、浏览器指纹；
- 跨站用户身份关联或行为轨迹追踪；
- 商品订单系统、库存系统或账号交付系统。

首期推广卡片不展示动态商品价格，避免与 GeoSub 的订阅价格数据混淆，也避免额外引入库存和价格同步责任。

## 3. 合规前置门禁

### 3.1 基本原则

广告位可以先开发，真实活动必须先审核。

审核应同时覆盖：

1. 推广文案；
2. 实际商品；
3. 商品来源；
4. 具体销售及交付方式；
5. 平台条款与转让权限；
6. 最终落地页及其可访问的相关销售内容；
7. 经营主体、售后说明和消费者信息。

“使用中性品牌文案”不能绕过商品审核。首页品牌入口如果指向包含未核验账号销售内容的商店首页，同样不能默认放行。

### 3.2 第三方账号专项审核

Google、Telegram 等第三方账号相关商品必须有可追溯证据，至少回答：

- 商品究竟是账号、订阅、兑换码、赠礼、代操作服务，还是其他权益？
- 来源是否清楚，供应方是否具有相应处分权限？
- 适用平台条款是否允许该类交易、转让、转售或交付方式？
- 是否存在地区、产品类型、组织账号或个人账号的限制？
- 是否涉及共享凭据、保留恢复入口、历史数据泄露或原持有人找回风险？
- 是否依赖虚假注册、身份冒用、未经许可的自动化或规避平台限制？
- 交付范围、使用限制、退款条件和售后责任是否清楚？

以下材料**不能单独证明允许转让**：

- 能够登录账号；
- 能够修改密码；
- 有采购付款记录；
- 供应商声称“一手”“稳定”；
- 市场上其他商家也在出售；
- 没有找到明确禁止条款。

必须区分“账号控制权”和“平台允许转让或销售的权利”。

Google 的一般条款要求遵守适用的服务附加条款；Telegram 也列出了可选服务的专门条款。因此，仅检查通用条款不足以给具体商品放行。[Google 服务条款](https://policies.google.com/terms?hl=zh-CN)、[Telegram 服务条款](https://telegram.org/tos)

**本文件不判定具体商品已经合规，也不将未找到禁止条款解释为获得许可。**

### 3.3 审核记录要求

每份审核记录至少包含：

- 商品与落地页范围；
- 平台、商品类型、适用地区；
- 证据文件引用；
- 官方条款链接、版本或核验日期；
- 转让或销售权限的判断依据；
- 审核结论、审核人、审核时间；
- 有效期及复核日期；
- 限制条件、拒绝或暂停原因。

不得在推广数据库中保存账号密码、验证码、恢复码、身份文件原件等不必要的敏感资料。证据放入现有受控存储，推广系统仅保存引用。

### 3.4 放行和失效规则

审核状态：

`未提交 → 待审核 → 通过 / 拒绝`

已通过记录还可变为：

`过期 / 撤销`

以下内容变化必须重新审核：

- 商品或交付方式；
- 目标域名、路径、实质性查询参数；
- 推广标题、正文、素材及商业承诺；
- 落地页主要内容；
- 供应来源或授权条件。

审核必须绑定不可变的活动版本，不能只保存一个长期有效的 `approved=true`。

发现商品权限不明、落地页被替换、投诉涉及账号来源或隐私等情况，应暂停相关活动；不得等待实验结束。

### 3.5 审核责任

Codex 可以整理证据、发现缺项和实现门禁，但不得：

- 自行签署商品合法性或平台授权结论；
- 伪造审批人或审批记录；
- 使用测试数据代替真实审核；
- 将本 PRD 视为商品审批文件。

如负责人无法提供充分依据，该活动保持关闭。其余已获审查通过的独立活动可按授权范围继续推进。

## 4. 现有架构只读审计

### 4.1 审计先于实现

首先阅读仓库已有开发规范、架构文档及适用的 `AGENTS.md`。

只读审计阶段不得：

- 改写业务代码；
- 执行数据库迁移；
- 安装或升级依赖；
- 运行具有写入副作用的初始化、构建或部署脚本；
- 连接生产数据库做写入；
- 修改线上后台、环境变量、DNS 或 CDN；
- 输出密钥或复制真实用户数据。

可以在约定文档位置形成审计交付物；“只读”指不改变业务系统及运行环境。

### 4.2 必须查明的内容

| 领域 | 审计问题 |
|---|---|
| 应用结构 | 单仓库还是多应用？前后台如何组织？ |
| 路由和国际化 | 三个目标页面如何被准确识别？语言如何解析？ |
| 渲染 | SSR、SSG、客户端渲染还是混合？ |
| 价格页面 | 价格表、FAQ 和首页主要入口由什么组件提供？ |
| 样式 | 设计变量、响应式断点、暗黑模式机制是什么？ |
| 后台 | 是否已有配置页、角色权限和审计日志？ |
| 数据 | 数据库、迁移、配置存储、事务能力是什么？ |
| 缓存 | CDN、页面缓存、接口缓存、重验证如何工作？ |
| 安全 | 鉴权、CSRF、输入校验、CSP 如何实现？ |
| 分析 | 事件平台、同意管理、过滤规则和保留期限是什么？ |
| 发布 | CI、测试环境、发布流程、回滚能力是什么？ |

### 4.3 审计交付物

交付一份架构审计报告，明确：

- 已确认事实及代码位置；
- 未确认事项；
- 可复用能力；
- 最小修改范围；
- 关键风险与依赖；
- 建议实现方案及替代方案。

文件名称和目录遵循仓库惯例，不提前假设存在某个 `src`、`app` 或 `admin` 目录。

## 5. RFC 技术设计要求

审计完成后，先形成 RFC，再进入功能实现。

RFC 至少回答：

1. 三个投放位置如何映射到真实路由、语言和产品 ID？
2. 配置如何存储，为什么符合现有架构？
3. 审核版本与运行状态如何分离？
4. 如何保证服务端与客户端一致执行限制？
5. 如何防止跨语言缓存污染？
6. 如何让关闭操作在规定时间内生效？
7. 静态页面是否需要动态配置层，代价是什么？
8. 后台权限、输入校验和审计如何复用？
9. 事件如何去重，哪些用户不采集？
10. 如何获得成交汇总而不引入跨站身份追踪？
11. 无数据、无权限、超时、审核过期时如何降级？
12. 如何灰度、回滚和保留兼容性？

至少比较：

- 复用现有数据库与后台；
- 复用现有 CMS 或配置中心；
- 现有基础不足时的最小新增模块。

不能仅为了三个广告位引入独立广告服务、消息队列或新的大型管理框架。

若现有项目没有安全后台，必须明确新增后台的成本和认证方案，不得部署无认证配置接口作为临时替代。

RFC 涉及新增外部服务、付费依赖、扩大数据收集或扩大投放范围时，必须取得相应明确授权。

## 6. 逻辑数据模型

以下是业务模型，不要求机械地建立同名数据库表。

### 6.1 全局配置 `PromotionSettings`

| 字段 | 含义 |
|---|---|
| `enabled` | 总开关，默认关闭 |
| `environment` | 当前环境隔离标识 |
| `config_version` | 配置版本 |
| `analytics_enabled` | 新增分析开关，默认关闭 |
| `updated_at / updated_by` | 最后修改信息 |

总开关必须是最高优先级门禁。生产与测试环境不得共用可变配置。

### 6.2 广告位 `Placement`

三个逻辑标识：

- `zh_home_brand`
- `zh_google_one_detail`
- `zh_telegram_premium_detail`

字段至少包括：

- 逻辑标识；
- 真实语言标识；
- 页面类型；
- 产品内部 ID，首页为空；
- 启用状态；
- 当前绑定的已审核活动版本；
- 灰度比例或实验配置。

硬约束：

- 首期最多三个固定广告位；
- 每个位置最多绑定一个活动版本；
- 一个目标页面最多渲染一个推广模块；
- 不允许通配符路由；
- 不允许后台创建任意新页面投放位置。

没有可用活动时直接隐藏，不向其他位置借用广告，不自动回退为通用品牌广告。

### 6.3 活动及版本 `Campaign / CampaignRevision`

| 字段 | 含义 |
|---|---|
| `campaign_id` | 活动稳定标识 |
| `revision_id` | 不可变内容版本 |
| `internal_name` | 后台管理名称 |
| `title / description / cta_text` | 纯文本展示内容 |
| `merchant_name` | 商店名称 |
| `destination_url` | 经审核的 HTTPS 目标 |
| `asset_ref` | 可选的受控素材 |
| `product_scope` | 对应商品或服务范围 |
| `review_id` | 绑定的审核记录 |
| `start_at / end_at` | 生效区间 |
| `created_by / created_at` | 创建信息 |

时间持久化使用 UTC；后台默认按 `Asia/Shanghai` 显示，并注明时区。

时间区间采用开始包含、结束不包含的规则。首期所有活动必须有结束时间，避免实验后无限期继续。

修改已审核内容应生成新版本。原版本保持可审计；涉及风险的修改应立即暂停原版本。

### 6.4 运行状态与审核状态分离

运行意图：

`draft / scheduled / active / paused / archived`

审核状态：

`pending / approved / rejected / expired / revoked`

最终是否展示必须实时综合计算，不能只依据 `active`。

示意规则：

```text
允许展示 =
  当前环境允许
  且全局开关开启
  且真实页面命中固定白名单
  且语言完全匹配
  且广告位开启
  且活动运行状态允许
  且当前时间在有效期内
  且当前版本审核通过且未过期、未撤销
  且落地页符合已批准范围
  且命中已批准的灰度或实验规则
```

任何必要条件缺失、校验异常或配置不可用，均不展示。

### 6.5 审计日志

记录：

- 操作者和时间；
- 操作对象及版本；
- 创建、修改、审批、暂停、恢复、归档；
- 总开关及分析开关变更；
- 变更前后差异；
- 操作原因和结果。

不得允许普通运营人员修改审核证据或删除审计日志。

### 6.6 成交汇总

如启用商店汇总导入，保存：

- 商店、活动、广告位；
- 日期、时区、币种；
- 已支付订单数；
- 退款订单数、退款金额；
- 销售额及其口径；
- 来源文件或接口批次；
- 数据更新时间、完整性状态。

不保存购买者身份、账号凭据或完整订单资料。导入应支持幂等更新和退款修正。

## 7. 后台配置

### 7.1 功能范围

后台至少提供：

1. 总开关与三个广告位开关；
2. 活动草稿及版本管理；
3. 商品与落地页审核记录；
4. 活动与广告位绑定；
5. 生效时间及结束时间；
6. 桌面、移动、浅色、暗色预览；
7. 基础数据汇总；
8. 操作审计；
9. 紧急关闭入口。

列表须明确显示“为什么没有投放”，例如：

- 总开关关闭；
- 审核未完成；
- 审核过期；
- 尚未开始；
- 活动结束；
- 广告位未绑定；
- 配置校验失败。

### 7.2 权限

逻辑权限至少区分：

- 查看；
- 编辑草稿；
- 审核；
- 启用和暂停；
- 全局紧急关闭。

优先映射现有角色体系，不强制引入新角色系统。

具备编辑权限不意味着具备审核或生产启用权限。紧急关闭应方便授权人员操作，不受普通审批流程拖延。

保存草稿不得隐式启用活动。编辑页面不得因默认勾选导致真实投放。

### 7.3 校验与并发

服务端必须重新校验所有输入，不能依赖前端表单。

要求：

- 使用版本号等机制防止并发覆盖；
- 内容变更产生新版本并触发重新审核；
- 活动绑定、启用等关联操作保持原子性；
- 报错不暴露内部凭据和敏感证据；
- 新增权限不足时返回明确错误。

### 7.4 目标链接安全

- 仅允许 HTTPS；
- 按已批准的域名和路径范围校验；
- 禁止用户信息段、危险协议、非批准端口和任意跳转参数；
- 查询参数采用白名单；
- 防止相似域名、子域名匹配错误和开放重定向；
- 预览和公共接口不返回审核材料。

若开发自动落地页检查功能，必须防止 SSRF，限制目标和重定向次数，禁止访问内网及云元数据地址。不得为检查链接任意抓取用户提交的 URL。

## 8. 前端设计

### 8.1 设计原则

- 使用 GeoSub 现有组件和设计变量；
- 清楚标注“自营推广”；
- 明确商店是商业入口；
- 不使用“官方授权”“GeoSub 官方推荐”等未经证实的表述；
- 不伪装为价格比较结果、系统提示或导航必经步骤；
- 不要求用户点击广告才能查看价格。

### 8.2 首页品牌入口

位于核心搜索、主要分类或产品发现入口之后，不抢占首屏核心任务。

示例文案，仅用于设计预览：

> 自营推广 · 轨道商店  
> 数字商品与服务  
> 查看商品说明、适用条件及售后规则。  
> 查看商店 →

示例文案不是正式审核结论。实际目标页面未获审核时，预览按钮不可指向真实交易页面。

### 8.3 产品详情页

放在完整的核心价格比较区域之后、FAQ 之前。

如果页面没有 FAQ，应放在主要价格内容之后的补充信息区，具体位置在 RFC 中以截图说明。

推广文案必须与已批准商品一致。“Google One 相关”或“Telegram Premium 相关”不能自动等同于“普通账号商品适合该页面”。

如果没有合适且通过审核的商品，该详情页不展示推广。

### 8.4 响应式与暗黑模式

至少覆盖：

- 320、375、768、1024、1440 像素视口；
- 浅色和暗色主题；
- 长标题、长商店名；
- 无图片、图片加载失败；
- 字体放大和 200% 缩放。

布局要求：

- 移动端纵向排布；
- CTA 易于触达，目标触控尺寸建议至少 44×44 CSS 像素；
- 不横向溢出；
- 正文与背景保持清晰对比；
- 键盘焦点可见；
- 支持语义化标题和链接；
- 不使用闪烁、自动播放或强动画。

### 8.5 性能与失败行为

- 使用轻量文本卡片作为默认方案；
- 如有图片，指定宽高并使用受控资源；
- 不加载商店第三方脚本或跟踪像素；
- 推广请求不得阻塞价格内容；
- 配置超时、异常或空结果时隐藏模块；
- 不显示面向用户的技术错误；
- 不留下明显空白框或骨架。

优先在首次布局前确定是否显示。不得先插入大块占位再移除，造成明显布局位移。

静态生成场景必须在 RFC 中解决“快速关闭”和“旧 HTML 残留”的冲突，不能声称修改数据库即可立即关闭全部缓存页面。

## 9. SEO 要求

1. 商业链接使用 `rel="sponsored nofollow"`。
2. 如新窗口打开，同时设置适当的 `noopener`。
3. 不改变页面标题、主标题、canonical、hreflang 和价格结构化数据。
4. 推广内容不得进入价格对比的 Product、Offer、FAQ 等数据结构。
5. 不在全站导航、页脚或其他语言页面重复加入商业链接。
6. 不把广告页面或预览页加入 sitemap。
7. 预览必须有访问控制；`noindex` 不能替代认证。
8. 不针对搜索引擎展示不同商品或文案。
9. 缓存键必须区分必要的语言、页面和配置版本，防止广告串到其他页面。
10. 不得为投放修改 robots 规则或删除原有搜索内容。

Google 建议使用 `sponsored` 标记广告或付费性质链接，并支持多个 `rel` 值。本项目统一保留 `sponsored nofollow`；这并不构成排名安全保证。[Google 商业外链标记说明](https://developers.google.com/search/docs/crawling-indexing/qualify-outbound-links)

## 10. 隐私与分析

### 10.1 最小采集原则

推广展示与分析采集分离：

- 用户拒绝非必要分析后，仍可看到符合条件的普通推广卡片；
- 拒绝分析不得影响价格比较或跳转；
- 不得为推广新建用户画像；
- 不使用持久跨站标识、浏览器指纹或账号身份关联。

上线前确认现有隐私机制、适用地区、处理目的及必要同意要求。中文页面不意味着访客只来自中国。

若现有机制无法覆盖新增分析，则保持分析关闭，并在实验报告中明确数据缺口。

### 10.2 基础事件

| 事件 | 触发规则 |
|---|---|
| `promotion_impression` | 卡片至少 50% 可见，且页面处于可见状态连续至少 1 秒 |
| `promotion_click` | 用户实际激活推广链接 |
| `promotion_error` | 系统级配置或渲染异常，不含敏感内容 |

事件字段限定为：

- 活动及版本 ID；
- 广告位；
- 允许的页面和产品标识；
- 语言；
- 实验 ID、分组；
- 临时页面实例 ID；
- 事件 ID、事件时间、配置版本；
- 经批准的粗粒度设备类别。

不发送：

- 用户账号、邮箱、电话号码；
- 搜索词和完整查询字符串；
- 账号商品凭据；
- 完整 referrer；
- 原始 IP 作为业务分析维度。

基础设施可能存在 IP 日志，必须单独审查日志保留和访问权限，不能因业务事件不含 IP 就宣称完全匿名。

### 10.3 去重和事件质量

- 每次页面实例内，同一活动版本最多记录一次有效曝光；
- 前端重渲染不得重复曝光；
- 页面离开可见状态时中断连续可见计时；
- 点击重试使用同一事件 ID；
- 接收端实施幂等去重；
- 原始点击次数与发生点击的页面实例数分开统计；
- 点击不等待分析请求成功；
- 禁止为凑齐漏斗而伪造曝光；
- 过滤内部测试、预览和已识别机器人；
- 限制事件字段长度、频率及允许枚举。

服务端收到事件不代表一定是真人行为。报告应承认机器人、拦截器和采样造成的偏差。

### 10.4 成交衡量

首期优先使用**活动级汇总归因**：

- 链接仅携带活动、广告位和来源等非用户级标识；
- 商店在已有且获批准的分析范围内记录来源；
- GeoSub 只接收按日汇总的支付、退款及金额；
- 不新增逐人点击 ID，不建立跨站用户路径。

必须确认商店是否保留来源字段。仅附加 UTM 参数不等于已经打通成交归因。

默认建议归因口径为：同一次商店访问中，从带来源参数的入口进入并完成支付。实际实现不支持时应如实说明，不虚构归因窗口。

如只支持活动级汇总，不得宣称已实现逐点击成交转化率；可报告“来源标记订单数”和“订单数/有效点击次数”，并注明它不是用户转化概率。

无可信订单数据时，成交指标标记为“不可用”，不得填零或据此宣布无成交。

### 10.5 保留期限

供 RFC 确认的默认建议：

- 原始推广事件：30 天；
- 按日聚合数据：180 天；
- 审核及操作日志：按现有制度确定。

落实自动清理、访问权限和必要的删除流程。不得用无限期保留作为默认设置。

## 11. 14 天实验设计

### 11.1 开始条件

正式实验开始前必须完成：

- 三个位置的代码和测试；
- 实际开启活动的审核；
- 生产部署及投放的独立授权；
- 数据验证；
- 基线冻结；
- 阈值和观察负责人确认；
- 结束时间配置。

如果仅部分活动获审查通过，实验只覆盖这些活动；未开启位置不能记作表现为零。

14 天从稳定投放和数据验证完成后开始。灰度验证期不自动计入。

### 11.2 实验方法

首期主要是可行性验证，不预设一定能得到统计显著的结论。

首页与详情页的访问意图不同，直接比较 CTR 只能说明观察差异，不能证明详情页投放带来因果提升。

若已有隐私合规且可靠的实验框架，可在各页面分别设置不展示推广的对照组。不得为了本项目单独建设持久用户跟踪体系。

如果没有现成框架：

- 采用页面级观察；
- 比较上线前后同类日期和页面；
- 同时记录流量来源、促销活动及外部变化；
- 明确结果为描述性结论。

### 11.3 指标定义

| 指标 | 定义 |
|---|---|
| 有效曝光 | 满足可见条件并去重的曝光事件 |
| 曝光后点击率 | 同一页面实例中有效曝光后发生点击的实例数 ÷ 有效曝光实例数 |
| 总有效点击 | 去重、过滤后的全部实际点击 |
| 来源标记支付订单 | 商店按约定口径归因的已支付订单 |
| 退款率 | 同一订单队列中已退款订单数 ÷ 已支付订单数 |
| 净收入 | 同口径支付金额减退款；不等于利润 |
| 核心任务完成率 | 使用现有事件定义的价格查询或比较完成率 |
| 页面质量 | 页面错误、LCP、INP、CLS |
| 搜索观察 | 目标页面自然搜索点击、曝光等已有指标 |

快速点击可能发生在曝光阈值达成之前，需计入总点击，但不强行计入“曝光后点击率”的分子。

金额按币种分别报告。若换算，必须注明汇率来源、日期及口径。

### 11.4 基线

优先使用上线前连续 14 天数据，并尽量匹配星期结构。

若没有历史数据：

- 可以先收集基线；
- 或开展有限的可用性试验；
- 不得把没有基线解释成“用户体验无影响”。

实验前预先确定指标、排除规则和决策条件，不得事后选择有利口径。

### 11.5 停止与复核条件

以下为项目建议阈值，需在 RFC 中结合现有基线冻结，并非已经测得的结果。

**立即关闭相关活动或总开关：**

- 非白名单页面出现推广；
- 未审核或审核失效活动被展示；
- 跳转至非批准目标；
- 出现隐私数据泄露；
- 推广导致核心价格内容无法正常使用；
- 商品权限或落地页出现实质性风险。

**暂停扩量并调查：**

- 同条件性能验证中，LCP 相对基线增加超过 200ms，或 CLS 增加超过 0.02；
- 有足够样本时，页面错误率增加 0.5 个百分点；
- 可比窗口内核心任务完成率相对下降超过 5%；
- 重复事件超过 1%，或关键字段缺失超过 1%。

上述指标需约定样本量、观察窗口和数据来源；低流量时优先结合复现结果、人工检查和错误日志判断，不机械套用百分比。

自然搜索变化只能作为调查信号，14 天通常不足以单独证明长期 SEO 影响。

### 11.6 节奏

| 时间 | 工作 |
|---|---|
| 实验前 | 完成基线、审核、演练和授权 |
| 第 1 天 | 检查范围、链接、事件和错误 |
| 第 2—3 天 | 核对曝光、点击去重及商店来源字段 |
| 第 7 天 | 中期检查，优先评估体验和风险 |
| 第 14 天 | 停止首轮投放并导出初步结果 |
| 后续 | 等退款观察窗口成熟后补充成交结论 |

首期活动默认在实验结束后自动停止。继续投放或延期需要明确决定，不自动延长。

如果中途修改素材、落地页、流量比例或商品，应记录新版本和时间，分段分析，不能混为同一稳定实验。

### 11.7 实验结论

只允许形成有证据支持的结论：

- 可继续小范围投放；
- 需要修改后重新试验；
- 数据不足，无法判断；
- 应暂停或停止。

扩大到新页面、其他语言或增加单页广告数，属于新范围，必须单独评审。

## 12. 测试与验收

### 12.1 范围测试

必须验证：

- 中文首页最多一个入口；
- Google One、Telegram Premium 中文详情页各最多一个；
- 其他产品、其他语言和其他页面全部不展示；
- 深链、刷新、语言切换、客户端导航均遵守限制；
- 大小写、尾斜杠、别名或查询参数不绕过匹配；
- 缓存命中不会串语言、串页面或串实验配置；
- 全局关闭后，所有目标页面停止展示。

### 12.2 审核与状态测试

覆盖：

- 未审核、拒绝、过期、撤销；
- 生效前、结束边界；
- 修改已审核内容后的新版本；
- 目标链接变更；
- 无活动、配置损坏、超时；
- 并发编辑和重复提交；
- 服务端拒绝绕过前端的非法启用。

### 12.3 安全测试

覆盖：

- 后台未登录和越权访问；
- 按现有鉴权方式验证 CSRF 防护；
- 文案、素材字段的 XSS；
- 危险 URL、开放重定向、域名匹配绕过；
- 公共接口泄露审核材料；
- 事件伪造、异常输入和请求限流；
- 商店汇总导入的认证与幂等；
- 日志中是否出现凭据和个人数据。

### 12.4 体验与性能验收

提供真实截图或可访问预览，覆盖：

- 桌面与移动；
- 浅色与暗色；
- 两个详情页和首页；
- 长文案和无图状态；
- 键盘操作、焦点和放大；
- 开启与关闭状态；
- 与基线可比的性能结果。

不得只以组件能渲染作为验收通过。

### 12.5 SEO 与分析验收

- 商业链接属性正确；
- canonical、hreflang、主要标题和结构化数据无意外改变；
- 非目标页面 HTML 与运行时均无推广；
- 曝光阈值和去重规则正确；
- 快速点击不被错误丢弃；
- 用户拒绝分析后不发送新增分析事件；
- 事件失败不阻止跳转；
- 预览和测试数据不进入生产报表；
- 无订单来源数据时正确显示不可用。

### 12.6 质量门禁

通过仓库既有的：

- 格式、类型和静态检查；
- 相关单元及集成测试；
- 构建与必要的端到端测试；
- CI 和既有安全检查。

新增测试重点保护投放范围、审核门禁、权限、缓存和事件口径，不为简单视觉改动堆积重复测试。

已有失败应记录并区分来源，不得为通过本项目而关闭原有门禁。

## 13. 灰度发布与回滚

### 13.1 独立门禁

生产上线分成三个独立动作：

1. 部署代码；
2. 执行必要的生产数据迁移；
3. 开启真实推广及分析。

任一动作的授权不自动包含其他动作。

即使代码已获准部署，默认总开关和分析开关仍应关闭。

### 13.2 推荐发布顺序

以下仅为预案，必须在获得明确授权后执行：

1. 测试环境部署并验收；
2. 验证数据变更兼容旧代码；
3. 生产部署，开关保持关闭；
4. 验证非广告业务正常；
5. 仅向授权内部预览展示；
6. 按批准方案逐步向真实流量开放；
7. 稳定后开始正式 14 天实验。

如现有平台支持可靠流量分配，可采用 5% → 25% → 100%，每档至少经过约定观察窗口及足够数据检查。

若没有可靠分流能力，不得伪造“5% 灰度”。可以采取单个已审核广告位逐步启用的方式，由负责人明确接受该方案。

所有用户和搜索引擎遵循相同的资格及分配逻辑，不按爬虫身份隐藏广告。

### 13.3 快速关闭目标

建议验收目标：

- 总开关关闭后，新请求在 60 秒内停止展示；
- 已打开且继续可见的页面在 60 秒内检查并移除；
- 后台页面恢复到前台时，先重新验证配置；
- 已过期配置不得无限回退使用。

RFC 必须明确这些目标如何覆盖 CDN、静态 HTML、客户端缓存及离线缓存。

无法达到时应提出有证据的替代时限供评审，不得写成“即时生效”。

### 13.4 回滚层级

优先顺序：

1. 暂停单个活动；
2. 关闭单个广告位；
3. 关闭总开关和必要的分析采集；
4. 清理相关缓存；
5. 必要时回滚应用代码。

数据库优先采用向后兼容的新增结构。代码回滚时通常保留新增表和字段，不立即执行破坏性删除。

回滚不得撤销已生效的审核撤销记录，或恢复已经失效的活动。

### 13.5 演练要求

测试环境实际演练：

- 活动关闭；
- 总开关关闭；
- 缓存失效；
- 配置服务异常；
- 应用代码回滚；
- 旧版本读取新增数据；
- 关闭后重新访问和已打开页面的行为。

记录实测生效时间、负责人和操作步骤。

本 PRD 不授权 Codex 在生产执行关闭、缓存清理或回滚。生产事故操作权限应在上线前明确授予负责人；Codex 仅在获得相应明确授权后执行。

## 14. 分阶段执行与交付

### 阶段 A：只读审计

交付：

- 架构审计；
- 三个目标位置的真实映射；
- 依赖与未知事项；
- 最小改动建议。

退出条件：没有把猜测写成事实；关键缺项明确列出。

### 阶段 B：RFC 与实施拆分

交付：

- 技术方案；
- 数据与状态模型；
- 权限、缓存、隐私方案；
- 页面原型或现有页面标注；
- 测试和发布回滚方案；
- 分阶段任务清单。

退出条件：按仓库流程完成必要评审，解决会影响架构的关键选择。

### 阶段 C：基础模型与后台

交付：

- 数据结构及隔离环境迁移；
- 活动版本和审核门禁；
- 后台配置、权限和审计；
- 总开关与广告位开关。

退出条件：门禁与权限测试通过，所有默认值保持关闭。

### 阶段 D：前端展示

交付：

- 三个精确位置接入；
- 响应式与暗黑模式；
- 安全链接和失败降级；
- 非目标页面回归验证。

退出条件：投放范围、截图和可访问性检查通过。

### 阶段 E：分析与实验准备

交付：

- 事件规范及实现；
- 数据质量核对；
- 成交汇总接入或明确不可用说明；
- 14 天实验登记；
- 基线与阈值。

退出条件：指标定义可复现，隐私机制符合已确认要求。

### 阶段 F：测试环境验收

交付：

- 测试结果；
- 视觉与性能证据；
- SEO 差异检查；
- 回滚演练；
- 剩余风险和发布清单。

退出条件：形成可评审候选版本；生产仍保持未发布或未开启状态。

### 阶段 G：生产授权后执行

仅在获得明确授权后：

- 执行指定生产部署；
- 执行单独授权的迁移；
- 启用指定已审核活动；
- 按批准方案灰度；
- 记录实验开始、结束时间及负责人。

不得把“方案接受”“可以开发”“合并代码”解释成生产投放授权。

## 15. 完成标准

### 15.1 开发完成

必须满足：

- 审计和 RFC 完整；
- 代码符合现有架构；
- 三个广告位准确实现；
- 审核和权限不可通过普通请求绕过；
- 总开关默认关闭；
- 响应式、暗黑模式和必要测试通过；
- 缓存及关闭时限已验证；
- 发布和回滚材料可执行。

开发完成不要求实际商品一定获准投放。

### 15.2 上线就绪

额外要求：

- 实际商品和目标页面审核有效；
- 隐私及数据处理方案确认；
- 活动文案及链接冻结；
- 实验口径、阈值和责任人确定；
- 回滚演练通过；
- 所需生产操作均已明确授权。

未满足时必须标记为“开发完成，尚不可上线”。

### 15.3 实验完成

必须交付：

- 三个位置分别的有效曝光及点击结果；
- 可用的成交、退款数据及成熟度；
- 核心体验、性能和错误变化；
- 搜索观察及其局限；
- 数据缺口和样本量限制；
- 继续、修改、延期或停止的建议。

不能因有点击就宣称商业化验证成功。

## 16. Codex 执行指令

将以下要求作为后续实施约束：

### 16.1 执行顺序

1. 确认实际仓库和适用开发规范。
2. 首先完成只读审计，不假设技术栈、路由、数据库和后台结构。
3. 基于审计完善 RFC，遵守仓库已有评审流程。
4. 复用现有架构，以最小改动实现三个固定广告位。
5. 将运行状态与审核状态分离，默认全部关闭。
6. 完成后台、前端、分析及必要测试。
7. 提供可评审代码、预览、验证结果和发布材料。
8. 在生产操作之前停在明确的授权边界。

### 16.2 明确禁止

未经额外明确授权，不得：

- 生产部署或触发会自动部署的合并；
- 执行生产数据库迁移或写入；
- 修改生产环境变量、DNS、CDN 或线上配置；
- 开启任何真实推广活动；
- 开启新增生产分析采集；
- 将测试审核记录变为真实审核；
- 扩大到其他语言、产品或页面；
- 增加单页广告数量；
- 添加第三方广告脚本或跨站身份追踪；
- 新建未经批准的付费服务；
- 发送营销邮件或通知外部人员；
- 声称商品已合规、Google 或 Telegram 已授权；
- 绕过或关闭已有 CI、安全和权限门禁。

### 16.3 缺失信息时的处理

- 缺少仓库：请求仓库位置，不能凭空生成符合实际架构的实现结论。
- 缺少商店域名或商品证据：继续隔离开发，保持链接占位和活动关闭。
- 缺少分析权限：完成接口和测试，保持生产采集关闭。
- 缺少成交数据：明确报告不可用，不能模拟真实成交。
- 缺少生产授权：提交上线就绪材料，不执行生产动作。

### 16.4 最终汇报格式

执行完成后，用简洁清晰的方式报告：

1. 实现了什么；
2. 修改范围；
3. 测试及验证结果；
4. 尚未确认的信息；
5. 当前开关和环境状态；
6. 是否存在生产变更；
7. 发布所需的具体授权和前置条件；
8. 回滚操作及实测生效时间。

任何未实际执行的验证、部署、审核或数据核验，都必须明确写为未完成，不能使用推测性的“应该没问题”代替证据。

**本项目的可接受首期结果，是一套审核约束明确、范围严格、体验克制、数据可解释、能够可靠关闭的推广能力。没有获得商品与发布授权时，保持关闭本身就是正确交付状态。**
