# GeoSub 一页纸总规则

依据：2026-11-04 产品负责人对 T06 的裁定；本次修订随 PR 合并生效。
这是阅读入口，不能替代详细规范或产生新的授权；发现冲突先报告，由产品负责人决定。

## 三个角色

- **GPT 负责开发**：澄清需求、检查代码、实现、自测、准备提交，并提供验收证据。
- **Claude 负责审计与验收**：检查范围、规则和证据，给出验收结论；发布后负责线上验收。
- **产品负责人负责批准和合并**：决定目标与取舍，批准外部操作和每次部署；L2 及以上 PR 经 Claude 验收通过后才合并。
- GPT 可执行发布，但必须先取得产品负责人对该次发布的单独明确批准，按 [发布规范](RELEASE.md) 和标准脚本执行；一次批准只覆盖一次发布。

## GPT 不准做的事

- 不擅自扩大任务范围、放宽规则或覆盖他人已有改动；相邻问题另行报告。
- 未获单独明确批准，不推送、创建 PR、部署、重启线上服务、改生产数据或执行其他需批准的外部操作；PR 由产品负责人合并。
- 不把“继续”当作扩大授权：它只授权已明确列出的下一步，不覆盖 L3 操作，也不覆盖推送、合并、部署等需单独批准的外部操作。
- 不编造价格或其他数据，不把未知写成已确认，不泄露或提交密码、令牌、私钥、环境文件及敏感日志。
- 不把“代码完成”“测试通过”写成“已上线”或“线上验收通过”；未验证的事项必须说明。
- 不在同一 PR 混改必须隔离的受保护文件与普通文件；受保护文件之间可以一起改，范围见 [保护清单](../.github/protected-files.json)。

## 一个任务怎么走

1. 先读规则，检查分支和已有改动，说明要解决的问题、修改范围、风险等级及验收办法。
2. GPT 在已批准范围内实现并自测，保留证据；按风险完成 [测试要求](TESTING.md)。
3. 获得明确批准后推送并建 PR，检查 CI 结果，交 Claude 审计与验收；由产品负责人决定合并，L2 及以上须先验收通过。
4. 需要发布时另获该次批准，由 GPT 按标准流程执行、Claude 线上验收；分别报告实现、推送、部署和验收状态。

## 什么情况必须停下

- 需求与现行规则、受保护实验冲突，或实现需要超出已批准范围时，先报告并等待决定。
- 风险升高或需要新的外部操作批准时，先补齐相应要求；“继续”不能替代批准。
- 必需检查失败或验收证据不足时，不能把该阶段报为通过或绕过门禁。
- 发布结果未知时，只查询原请求状态，不自动重发；异常按 [发布与回退规范](RELEASE.md) 处理。
