审计桥接由 SQL schema:059 和 Prisma 20261026090000 同内容登记，可信设备为
Prisma 20261028090000。三个执行文件对应两项逻辑变更；schema 与 Prisma 双入口重复执行已验证。
两份 sql/isolated 采集候选仍不登记、不启用；本清单没有批准历史恢复或数据回填。

发现并修复：标准 SQL runner 使用 psql 逐句执行，顶层 SET LOCAL 没有外层事务，原锁限时无效。
现将 set_config('lock_timeout', '5s', true) 放在同一 DO 块的 LOCK 之前；未改变审计身份规则。
真实锁争用中，原版等到 9 秒 statement_timeout（57014），修正版约 5 秒按 lock_timeout（55P03）退出。
失败保持原子性；释放锁后重试成功，下一句 lock_timeout 恢复默认，历史合成行不变。
standalone psql 回归已接入既有 audit compatibility 测试，因此内容数据库 CI 会实际执行它。

修正后桥接两个文件的 SHA-256 相同：

`2ef1f35b47461096ad4756a2f90ef3654d8c1ad6c6c16221093cbf00afc980e1`

此为尚未获准应用于生产的候选迁移源码修正，允许清单与规范登记已同步。
没有改写任何既有数据库的迁移账本；若生产已经登记不同校验和，必须停止并核对，不覆盖账本。

## 获得后续授权后的执行顺序

1. 确认最终提交已推送且对应 CI 全通过；按审查结果合并。生产预检通过后单独批准迁移与部署。
2. 使用标准 geosub_ops.py / rolling 控制入口；先完成内容回退预检，再关闭写入围栏并等待在途任务。
3. 需要迁移时暂停对应任务、创建并验证实际生产备份；使用标准 schema → Prisma baseline → migrate deploy。
4. 完成数据库检查、候选健康与内容源站核对后切换网站；保留构建与静态资源。
5. 网站与采集器数据库输入一致后，走独立采集组件入口；原来关闭的定时器保持关闭。
6. 抽样一个产品验证真实采集 → 自动审核 → 正式价格 → 前台展示，官网与 App Store 分开核对。

锁超时或迁移失败时，保留证据并停止，不自动重发；核对失败迁移状态后再决定重试。
应用回退使用保留构建，前提是精确内容回退门禁通过；保留增量列、表及历史，不自动恢复数据库。
数据库恢复仅用于独立批准的数据恢复窗口。未知远程执行结果通过原请求 status 查询，不重复启动。
