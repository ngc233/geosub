# GeoSub 小团队开发流程

状态：v2.11 小团队规范基线

生效日期：2026-08-27

适用团队：产品负责人 + Codex 主执行 + Claude 辅助评审

## 1. 目的

GeoSub 当前由一名产品负责人和 AI 开发协作者持续建设。流程的目标是让少量成员快速、可靠地交付，而不是模拟大公司的岗位、会议和逐级审批。

本流程坚持两点：

1. 删除不产生决策或证据的形式工作。
2. 不降低生产、数据、SEO、安全和回退底线。

规范基线版本不等于应用版本。仅更新本流程不需要修改 `VERSION`，也不需要部署生产服务器。

## 2. 团队角色

### 2.1 产品负责人

- 决定产品目标、优先级和最终取舍。
- 批准 GitHub 推送、生产部署、生产数据操作和其他外部状态变更。
- 对存在多条合理产品路线的事项作最终选择。

### 2.2 Codex

- 默认承担需求澄清、代码检查、实现、测试、提交准备、发布执行和结果复核。
- 每次开发前主动读取本规范及任务相关规范，不要求产品负责人重复提醒。
- 在已批准的计划和安全边界内，用户说“继续”时直接推进，不重复询问相同授权。
- 保留用户已有改动，明确区分已验证、结构性检查和未验证事项。

### 2.3 Claude

- 作为可选的第二分析视角，用于架构、SEO、数据模型、重大设计方向或产品负责人明确要求的复核。
- 不参与每个普通 Bug、样式修复或文档修改。
- Claude 的建议属于输入，不替代仓库事实、自动测试、真实数据或生产验收。

## 3. 双重分类

开始实现前，只需确定“工作类型”和“风险等级”。低风险任务可以在工作更新中简要说明，不强制新建文档。

### 3.1 工作类型

- **Bug**：已确认行为与规范、数据或预期不一致。
- **Improvement**：在现有能力内改善体验、质量或效率。
- **Feature**：增加新的用户能力、入口或输出。
- **Architecture**：改变跨模块约束、数据模型、缓存、依赖边界或发布链路。

### 3.2 风险等级

| 等级 | 典型范围 | 最低流程 |
| --- | --- | --- |
| L0 | 文档、报告、注释、只读诊断 | 阅读相关规范、检查工作树、检查差异 |
| L1 | 局部 Bug、可逆样式或文案、单组件交互、测试修复 | 明确范围与不变项、聚焦测试、受影响代码门禁；UI 做目标页面四态验收 |
| L2 | 共享组件、多页面行为、路由、SEO 元数据、数据读模型、依赖、CI 或发布脚本 | 简短任务说明、完整相关测试、生产构建；推送后通过 CI，并说明回退和观察项 |
| L3 | 生产数据库、迁移、批量回填、凭据、部署、破坏性操作、索引政策或架构变更 | 明确批准、RFC 或等价决策记录、备份/迁移/回退方案、真实环境验收 |

如果范围在执行中跨级，先报告升级原因，再补齐新等级要求。不得为了省流程把 L2/L3 拆成多个伪装的 L1。

## 4. 文档要求

- L0/L1 Bug 和 Improvement：用户请求、工作更新和提交说明足以形成记录，不强制 PRD。
- L1 Feature：需要简短任务说明，至少写清用户问题、范围、不变项和验收标准。
- L2 Feature：需要轻量 PRD；只写影响当前决策的内容。
- L2 Architecture：需要轻量 RFC，说明选择、影响、迁移和回退。
- L3：必须至少有一种与变更性质匹配的持久记录，例如 PRD、RFC、运行手册或等价决策记录。

不为同一决定重复创建报告、计划、PRD 和 RFC。已有规范可以回答的问题直接引用，不重新抄写。

## 5. 默认工作流

1. **读取**：自动读取 `AGENTS.md`、本文件、产品与工程规则，以及任务相关规范。
2. **盘点**：检查分支、工作树、当前实现、数据和相关测试，保护未知改动。
3. **定界**：确定类型、风险、范围、不变项和最低验收；L0/L1 可在一句工作更新中完成。
4. **实现**：优先复用现有组件、数据模型和脚本，不顺手整改相邻问题。
5. **验证**：按风险执行聚焦测试、构建、浏览器、数据、SEO 或生产验收。
6. **交付**：一个提交解决一个明确问题；本地实现、GitHub 推送和生产部署分别报告。
7. **观察**：只有存在 SEO、数据、性能或生产运行窗口时才建立后续观察项。

## 6. 授权边界

以下本地、可逆且在需求范围内的操作默认继续执行：

- 阅读文件和日志、检查 Git 状态、运行测试和只读诊断。
- 编辑已批准范围内的代码和文档。
- 创建临时测试环境并在完成后清理明确由本任务创建的临时资源。

以下操作仍需产品负责人明确批准：

- 推送 GitHub、创建或合并 PR。
- 生产部署、重启生产服务或修改定时任务。
- 生产 SQL、迁移、回填、恢复和批量内容变更。
- IndexNow、站长平台、外部消息和其他第三方状态变更。
- 删除未知文件、覆盖工作树或使用破坏性 Git 操作。

授权只覆盖已说明的目标和范围，不自动扩展到相邻操作。

## 7. 验证原则

- 测试与改动风险匹配，不以固定仪式代替判断。
- L0 文档改动通常只需链接、格式、范围和差异检查。
- L1 只验收受影响组件和代表页面，不重复全站人工巡检。
- L2 运行完整相关自动化和生产构建；获得推送批准后再以 CI 验收远端环境。
- L3 增加备份、迁移、回退和真实生产验证。
- 所有用户可见 UI 仍需覆盖受影响页面的 Desktop / Mobile / Light / Dark；不要求无关页面重复验收。
- 自动测试、浏览器、数据库、SEO 和生产证据不能互相冒充。

## 8. 完成标准

一项工作可以宣布完成，必须同时满足：

- 批准范围已实现，没有夹带无关修改。
- 对应风险等级的验证已通过，未验证项已明确列出。
- 用户已有改动保持不变，工作树和暂存区范围清楚。
- 需要提交时，提交内容单一且可追溯。
- 需要推送或部署时，远端提交、CI、线上版本和回退点按实际状态报告。

没有运行生产部署的任务，不得写成“已上线”；不影响运行时的文档、测试或 CI 修改，不需要为了流程完整而部署服务器。

## 9. 沟通方式

- 工作更新以结论、当前证据和下一步为主，不重复长篇计划。
- 遇到真实冲突、范围升级或需要新授权时才暂停。
- 相邻问题记录为后续项，不在当前任务中自动扩展。
- 完成报告保持简洁；只有 L2/L3 或用户要求时才生成正式报告。
